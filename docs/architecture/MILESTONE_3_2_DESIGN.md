## Executive Summary

Milestone 3 implemented unified tri-source retrieval (Episodic, Semantic, Knowledge Graph), and Milestone 3.1 conducted an independent statistical audit and ablation study. The empirical audit uncovered four fundamental architectural insights:

1. **Episodic Memory Superiority:** Pure episodic retrieval currently outperforms all fused configurations (43.33% binary accuracy vs 40.00% fused, and 55.44% fact coverage vs 52.75% fused), with Recall@5 reaching **98.33%**.
2. **Context Crowding / Displacement:** In a rigid top-$k=5$ budget, injecting semantic memory items directly into the primary candidate list displaces neighboring conversational turns that the local LLM needs for narrative context.
3. **Graph Double-Edged Sword:** Universal injection of Knowledge Graph triples produces **zero net binary gain** across the benchmark ($40.00\% \to 40.00\%$, $p = 1.0$). While it solves specific multi-hop connections (e.g., `cmf02`), it injects misleading distractor triples on historical-state queries (e.g., `h03`), degrading accuracy.
4. **Context Truncation & Over-Abstention:** 30% of system failures stem from LLM over-abstention (false refusal despite facts present in context), and 25% stem from cross-session context truncation under rigid $k=5$ limits.

**Milestone 3.2 establishes the architectural blueprint for Adaptive Retrieval**:
- **Adaptive Query Routing:** A lightweight, two-stage hybrid classifier that routes queries to optimal retrieval channels, keeping Episodic memory as the default backbone and activating the Knowledge Graph strictly when multi-hop relational bridging is required.
- **Adaptive Evidence Selection:** A layered Primary/Auxiliary context assembly that treats episodic dialogue turns as the primary narrative spine and anchors semantic facts as non-displacing metadata annotations, adapting context budgets dynamically to query complexity.
- **Knowledge Graph Safeguards:** Entity disambiguation, temporal interval filtering on graph edges, and distractor suppression to eliminate false context injection.
- **Statistically Rigorous Evaluation Protocol:** A two-split evaluation protocol separating tuning from testing, with scaled sample sizes per category (including 25 unanswerable questions) and exact paired significance testing.

## 1. Statistical Audit Verification & Correction

### 1.1 Formal Addendum to Milestone 3.1 Paired Binary McNemar Counts
During the independent audit of `MILESTONE_3_1_AUDIT_REPORT.md`, an analysis of the raw statistical artifacts in `evaluation/milestone_3_1_audit/phase2_statistical_analysis.json` revealed a typographical transcription error in the markdown table of Section 2.1:
- The markdown table text listed discordant pairs as `Discordant (11 vs 3)`, `(9 vs 3)`, and `(9 vs 3)` for Arms B, D, and E against Arm A.
- The **true computed counts** generated by Python in `phase2_statistical_analysis.json` were:
  - **Arm B (Episodic Only):** $b = 10$ wins, $c = 2$ losses ($N_{\text{disc}} = 12$, net gain $+8 / 60 = +13.33\%$).
  - **Arm D (Episodic + Semantic):** $b = 7$ wins, $c = 1$ loss ($N_{\text{disc}} = 8$, net gain $+6 / 60 = +10.00\%$).
  - **Arm E (Unified Tri-Source):** $b = 8$ wins, $c = 2$ losses ($N_{\text{disc}} = 10$, net gain $+6 / 60 = +10.00\%$).

### 1.2 Mathematical Verification of Exact Two-Sided McNemar Tests
Evaluating conventional two-sided exact binomial tests on the true counts versus typographical counts:

$$\text{Arm B (True: 10 vs 2): } p = 2 \times \sum_{k=10}^{12} \binom{12}{k} (0.5)^{12} = \frac{158}{4096} = \mathbf{0.03857} \quad (\text{Significant at } \alpha = 0.05)$$
$$\text{Arm B (Typo: 11 vs 3): } p = 2 \times \sum_{k=11}^{14} \binom{14}{k} (0.5)^{14} = \frac{940}{16384} = 0.05737 \quad (\text{Not significant at } \alpha = 0.05)$$
$$\text{Arm D (True: 7 vs 1): } p = 2 \times \sum_{k=7}^{8} \binom{8}{k} (0.5)^{8} = \frac{18}{256} = \mathbf{0.07031} \quad (\text{Marginally significant at } \alpha = 0.10)$$
$$\text{Arm E (True: 8 vs 2): } p = 2 \times \sum_{k=8}^{10} \binom{10}{k} (0.5)^{10} = \frac{112}{1024} = \mathbf{0.10938} \quad (\text{Not significant at } \alpha = 0.10)$$

**Key Audit Takeaway:**  
The reported $p$-values in the M3.1 audit report (`0.0386`, `0.0703`, `0.1094`) were mathematically exact and generated from the true counts ($10\text{ vs }2, 7\text{ vs }1, 8\text{ vs }2$). The typographical transcription error in the display text has been formally corrected in [STATISTICAL_AUDIT_CORRECTION.md](file:///c:/Users/Krishna/Desktop/Brahmaand/Coding_Ki_Dunia/Projects/IVARA/evaluation/milestone_3_1_audit/STATISTICAL_AUDIT_CORRECTION.md).

### 1.3 Correction on the Unanswerable Question Category
The M3 and M3.1 reports noted 100% accuracy on unanswerable questions.
- **Statistical Reality:** The stratified sample contained only **5 unanswerable questions** ($n=5$).
- The Wilson score 95% confidence interval for 5/5 correct abstentions is **$[56.6\%, 100.0\%]$**.
- **Corrected Finding:** While zero false acceptances were observed, an $n=5$ sample with a lower confidence bound of 56.6% is statistically underpowered. Claims of "perfect refusal calibration" are scientifically overstated and must be validated on an expanded unanswerable suite ($N \ge 25$).

## 2. Adaptive Query Routing Architecture

```
+--------------------------------------------------------------------------------------------------+
|                                        INCOMING USER QUERY                                       |
+--------------------------------------------------------------------------------------------------+
                                                 |
                                                 v
                       +---------------------------------------------------+
                       |             STAGE 1: FAST RULE-BASED              |
                       |                FEATURE EXTRACTOR                  |
                       |                 (Latency < 2 ms)                  |
                       +---------------------------------------------------+
                       | * Temporal Pattern Regex (years, relative markers)|
                       | * Relational & Bridge Tokens ("who managed", etc.)|
                       | * Negative & Refusal Tokens ("did he ever", etc.) |
                       | * Entity Overlap Count (SQLiteGraphStore scan)    |
                       +---------------------------------------------------+
                                                 |
                        +------------------------+------------------------+
                        | (High Confidence >=0.85)                        | (Low Confidence <0.85)
                        v                                                 v
         +-----------------------------+                   +-----------------------------+
         |     DETERMINISTIC ROUTE     |                   |  STAGE 2: HYBRID CLASSIFIER |
         |   Immediate Intent Vector   |                   |  Lightweight Vector / Probe |
         +-----------------------------+                   +-----------------------------+
                        |                                                 |
                        +------------------------+------------------------+
                                                 |
                                                 v
+--------------------------------------------------------------------------------------------------+
|                                    RESOLVED QUERY CATEGORY                                       |
+--------------------------------------------------------------------------------------------------+
| Category               | Episodic Channel  | Semantic Channel  | Graph Channel    | Context Mode |
+------------------------+-------------------+-------------------+------------------+--------------+
| single_fact            | ACTIVE (Primary)  | ACTIVE (Auxiliary)| DISABLED         | Minimal (k=3)|
| historical_state       | ACTIVE (Primary)  | ACTIVE (Auxiliary)| DISABLED (Guard) | Point-in-Time|
| temporal_longitudinal  | ACTIVE (Primary)  | ACTIVE (Auxiliary)| DISABLED         | Chronological|
| cross_session_synth    | ACTIVE (Primary)  | CONDITIONAL       | DISABLED         | Multi-Session|
| entity_relationships   | ACTIVE (Primary)  | ACTIVE (Auxiliary)| ACTIVE (Targeted)| Relational   |
| multi_hop_reasoning    | ACTIVE (Primary)  | ACTIVE (Auxiliary)| ACTIVE (Bridged) | Multi-Hop    |
| negative_information   | ACTIVE (Primary)  | ACTIVE (Auxiliary)| DISABLED         | Strict Refusal|
| unanswerable           | ACTIVE (Probe)    | ACTIVE (Probe)    | DISABLED         | Sufficiency  |
+--------------------------------------------------------------------------------------------------+
```

### 2.1 Intent Categories and Routing Specifications

#### 1. `single_fact_retrieval`
- **Definition:** Specific biographical property of an entity (e.g., date of birth, graduation date, alma mater).
- **Episodic Channel:** Active (Primary). Returns top-3 turns.
- **Semantic Channel:** Active (Auxiliary). Provides exact structured fact.
- **Graph Channel:** **DISABLED**. Single facts do not require relational traversal.

#### 2. `historical_state_retrieval`
- **Definition:** State or property prior to an update (e.g., "Where did Arjun live in late 2024?").
- **Episodic Channel:** Active (Primary). Context window expansion with temporal date bounds.
- **Semantic Channel:** Active (Auxiliary). Provides historical records with `valid_to` timestamps.
- **Graph Channel:** **STRICTLY DISABLED**. Prevents injection of current-state distractor triples (the root cause of failure `h03`).

#### 3. `temporal_longitudinal`
- **Definition:** Sequence of events, ordering, or duration (e.g., "Did Arjun adopt Neovim before moving to Zurich?").
- **Episodic Channel:** Active (Primary). Context expansion enabled; chronological sorting enforced.
- **Semantic Channel:** Active (Auxiliary). Valid-time interval checking.
- **Graph Channel:** **DISABLED**. Sequence reasoning is grounded in conversational timestamps.

#### 4. `cross_session_synthesis`
- **Definition:** Aggregating facts across multiple distant sessions (e.g., "Trace Arjun's career transitions across all companies").
- **Episodic Channel:** Active (Primary). Expanded multi-session budget ($k=8\text{ to }10$). Session diversity cap relaxed to 2 turns per session across up to 4 sessions.
- **Semantic Channel:** Active for summary synthesis.
- **Graph Channel:** **DISABLED**. Prevents entity graph explosion across unrelated milestones.

#### 5. `entity_relationships`
- **Definition:** Direct relational links between two entities (e.g., "What is the relationship between Dr. Shalini Verma and Arjun?").
- **Episodic Channel:** Active (Primary). Retrieves conversational introduction.
- **Semantic Channel:** Active (Auxiliary). Extracts predicate triples.
- **Graph Channel:** **ACTIVE**. Seeded with both entities; executes 1-hop direct relationship traversal.

#### 6. `multi_hop_reasoning`
- **Definition:** Relational chain requiring an intermediate bridge entity (e.g., "In which city does the manager who supervised Arjun's Go caching work reside?").
- **Episodic Channel:** Active (Primary). Fetches target dialogue context.
- **Semantic Channel:** Active (Auxiliary). Provides entity properties.
- **Graph Channel:** **ACTIVE**. Executes bounded 2-hop traversal anchored at query entity to discover bridge entity (e.g., Arjun $\to$ CacheMesh $\to$ Vikram Rao $\to$ Bengaluru).

#### 7. `negative_information`
- **Definition:** Determining non-occurrence or negative preferences (e.g., "Did Arjun undergo knee surgery?").
- **Episodic Channel:** Active (Primary). Retrieves turns discussing the negative condition.
- **Semantic Channel:** Active (Auxiliary). Checks for negated claims.
- **Graph Channel:** **DISABLED**. Knowledge graphs are positive-assertion systems and do not reliably represent negative assertions.

#### 8. `unanswerable_questions`
- **Definition:** Inquiries regarding facts or entities not present in memory.
- **Episodic Channel:** Active for initial probing ($k=3$).
- **Semantic Channel:** Active for entity probing.
- **Graph Channel:** **DISABLED**. If zero seed entities are resolved, graph traversal is bypassed entirely.

## 3. Adaptive Evidence Selection Algorithm

### 3.1 Primary Spine vs. Auxiliary Annotation (Solving Context Crowding)
In Milestone 3, treating episodic turns and semantic memories as flat competitors in RRF caused semantic items to crowd out contiguous dialogue context (-3.33% binary accuracy).

Milestone 3.2 redesigns context assembly into a **Two-Tier Primary/Auxiliary Model**:

```
+--------------------------------------------------------------------------------------------------+
|                                    ADAPTIVE EVIDENCE CONTEXT                                     |
+--------------------------------------------------------------------------------------------------+
|                                                                                                  |
| [TIER 1: PRIMARY EPISODIC SPINE]                                                                 |
| Session Cluster: session_04 (November 12, 2024)                                                  |
|   ├── [Turn 1 - Preceding] Speaker: Arjun Mehta (user): "I am finalizing the apartment lease."   |
|   ├── [Turn 2 - Target]    Speaker: Arjun Mehta (user): "Moved into HSR Layout Sector 2 today."  |
|   │     └── [AUXILIARY ANNOTATION - Memory m008]:                                                |
|   │           Fact: lives_in(Arjun Mehta, HSR Layout Sector 2) [Valid: 2024-11-12 to 2026-09-01]  |
|   └── [Turn 3 - Succeeding] Speaker: Assistant: "Noted your new address in HSR Layout."          |
|                                                                                                  |
| [TIER 2: TARGETED GRAPH TRIPLES] (Conditioned on Category = entity_rel / multi_hop)             |
|   └── (Arjun Mehta) --[works_at {role: "Associate Software Engineer"}]--> (HyperScale Systems)   |
|         [Source: turn_012, Valid: 2022-07-01 to 2025-02-01]                                      |
+--------------------------------------------------------------------------------------------------+
```

### 3.2 Dynamic Context Budgeting
Instead of a static $k=5$, context budgets are dynamically allocated based on query complexity:

| Category | Primary Episodic Turns | Context Expansion ($\pm w$) | Max Sessions | Auxiliary Semantic Limit | Graph Triples Limit | Target Token Budget |
|:---|:---:|:---:|:---:|:---:|:---:|:---:|
| `single_fact` | 2 | $\pm 0$ | 1 | 2 (Inline) | 0 | $\sim 250$ tokens |
| `historical_state` | 3 | $\pm 1$ | 2 | 2 (Inline) | 0 | $\sim 400$ tokens |
| `temporal_longitudinal`| 4 | $\pm 1$ | 2 | 2 (Inline) | 0 | $\sim 500$ tokens |
| `cross_session_synth` | 8 | $\pm 0$ | 4 | 3 (Inline) | 0 | $\sim 800$ tokens |
| `entity_relationships`| 3 | $\pm 1$ | 2 | 2 (Inline) | 3 | $\sim 500$ tokens |
| `multi_hop_reasoning` | 4 | $\pm 1$ | 2 | 2 (Inline) | 4 | $\sim 600$ tokens |
| `negative_information`| 2 | $\pm 1$ | 1 | 1 (Inline) | 0 | $\sim 300$ tokens |
| `unanswerable` | 2 | $\pm 0$ | 1 | 0 | 0 | $\sim 150$ tokens |

## 4. Knowledge Graph Safeguards

Milestone 3.1 identified that unconstrained graph injection introduces harmful distractor triples (e.g. `h03`). Milestone 3.2 implements five mandatory graph safeguards:

### 4.1 Temporal Interval Filtering on Graph Edges
Every relationship edge stored in `SQLiteGraphStore` must record:
- `valid_from`: ISO timestamp when fact became true.
- `valid_to`: ISO timestamp when fact was superseded (or `NULL` if current).

When the query router detects a historical-state or point-in-time constraint (e.g., "initial", "in 2024"), graph traversal filters edges against the target interval:
$$[t_{\text{query\_start}}, t_{\text{query\_end}}] \cap [\text{edge.valid\_from}, \text{edge.valid\_to}] \neq \emptyset$$
Triples outside the temporal window are pruned before fusion.

### 4.2 Lexical & Semantic Distractor Suppression
A retrieved graph triple $(u \xrightarrow{r} v)$ is suppressed if neither the target node $v$ nor the predicate $r$ has lexical or embedding similarity with the query tokens:
$$\text{Relevance}(u \xrightarrow{r} v, Q) = \max \left( \text{Sim}(v, Q), \text{Sim}(r, Q) \right) \ge \tau_{\text{graph}} \quad (\tau_{\text{graph}} = 0.45)$$

### 4.3 Provenance Grounding Verification
A graph triple is never treated as standalone unquestionable truth. Every triple must carry its `source_turn_id` or `source_memory_id`. If a triple cannot be resolved to an underlying dialogue turn or verified semantic memory, its confidence score is discounted by 50%.

### 4.4 Entity Disambiguation and Alias Resolution
Queries matching multiple candidates (e.g., "Aetheria" vs "Aetheria Europe research office") are disambiguated by matching entity types (`Company` vs `Office`) against query nouns.

## 5. Fair Evaluation Protocol for Milestone 3.2

To avoid overfitting and provide statistically definitive conclusions, Milestone 3.2 establishes a strict two-split evaluation protocol:

### 5.1 Dataset Split Architecture
1. **Development Set ($N = 60$):**
   - 5 questions per category across 12 categories.
   - Used exclusively for tuning routing heuristic thresholds, confidence cutoffs ($\tau_{\text{graph}}$), and context budgets.
2. **Held-Out Test Set ($N = 145$):**
   - **Completely sealed** during development.
   - 10 questions per category across 12 categories ($120$ questions).
   - **Expanded Unanswerable Category ($N = 25$):** Specifically expanded from 5 to 25 questions to enable statistically valid abstention evaluation (Wilson 95% CI width $\le \pm 15\%$).

### 5.2 Comparative Experimental Arms
The benchmark will evaluate five standardized arms on the held-out test split:
- **Arm A (Episodic Only Baseline):** Pure conversation turns with context expansion.
- **Arm B (Semantic Only Baseline):** Pure extracted semantic facts via unified pipeline.
- **Arm C (Fixed Fusion Baseline):** Milestone 3 baseline (static RRF-P fusion across all three channels).
- **Arm D (Conditional Graph Retrieval):** M3 fusion with graph gated strictly on multi-hop/relational queries and temporal safeguards.
- **Arm E (Fully Adaptive Retrieval):** Full hybrid routing, layered Primary/Auxiliary context selection, adaptive context budgeting, and graph safeguards.

### 5.3 Target Metrics & Statistical Standards
- **Accuracy Metrics:** Fact Coverage (continuous), Binary Accuracy ($\ge 0.70$), Exact Match ($\ge 0.99$).
- **Retrieval Metrics:** Recall@5, MRR, Evidence Coverage.
- **Abstention Metrics:** Correct Abstention Rate, False Acceptance (Hallucination on unanswerable), False Rejection (Over-abstention on answerable).
- **Graph Safety Metric:** Graph-Induced Harmful Changes Count (regressions caused by graph injection).
- **Latency Profiling:** End-to-end response latency (ms) and standalone retrieval latency (ms).
- **Significance Testing:** Two-sided exact McNemar test for binary accuracy, Wilcoxon signed-rank test for fact coverage, and 10,000-resample bootstrap 95% confidence intervals.

## 6. Risks, Trade-Offs & Implementation Sequence

### 6.1 Architectural Trade-Offs
| Design Choice | Benefit | Trade-off / Risk | Mitigation |
|---|---|---|---|
| **Lightweight Deterministic Router** | $< 2\text{ ms}$ routing latency, zero API cost | Edge-case misclassifications | Hybrid fallback to vector prototype similarity on low confidence |
| **Layered Context Budgeting** | Prevents semantic facts from displacing dialogue context | Slightly larger prompt payloads on multi-session queries | Adaptive budget caps; $k=3$ for single-fact queries saves tokens |
| **Conditional Graph Gating** | Eliminates distractor injections like `h03` | May miss serendipitous associative links | Conservative gate: activate whenever $\ge 2$ entities are detected |

### 6.2 Phased Implementation Sequence
1. **Batch 1 — Router & Classifier:** Implement `AdaptiveRouter` with deterministic regex and entity overlap signals; unit test on development split.
2. **Batch 2 — Layered Evidence Selector:** Implement `AdaptiveEvidenceSelector` in `src/unified_retrieval/` supporting Primary Episodic Spine and Auxiliary Semantic Annotations.
3. **Batch 3 — Graph Safeguards:** Add temporal interval filtering and distractor suppression to `GraphRetriever`.
4. **Batch 4 — Answering Prompt Calibration:** Refine system prompt sufficiency instructions to mitigate local LLM over-abstention.
5. **Batch 5 — Controlled Benchmark Execution:** Run the five-arm comparative evaluation on the sealed 145-question held-out test split.
